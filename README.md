# Личный финучёт

## 1. Назначение и сценарии
**Цель:** Приложение для базового учета личных доходов и расходов.

**Пользовательские сценарии:**
- Просмотр текущего баланса и краткой сводки за месяц на главном экране.
- Просмотр общего списка доходов и расходов.
- Навигация по основным разделам учета (транзакции, категории, бюджеты).
- Добавление и удаление операций, фильтрация и поиск по ним.
- Создание категорий доходов и расходов.
- Задание месячных лимитов (бюджетов) на категории расходов и контроль их превышения.
- Регистрация, вход и выход; данные каждого пользователя видны только ему.

**Основные экраны:**
- `/` — Обзор (Dashboard)
- `/transactions` — Транзакции
- `/categories` — Категории
- `/budgets` — Бюджеты
- `/reports` — Отчёты
- `/login`, `/register` — вход и регистрация (публичные)

## 2. Стек и реализация
- **Frontend:** React + TypeScript + Vite, React Router DOM, Material-UI
- **Backend:** Python + FastAPI, Pydantic, pydantic-settings, PyJWT, pwdlib (Argon2)
- **База данных:** PostgreSQL, SQLAlchemy 2.0

## 5. Структура frontend
Используется упрощённая структура на основе Feature-Sliced Design.

```
frontend/src/
├── main.tsx            # точка входа
├── app/                # настройка приложения: маршруты, провайдеры, тема, layout с меню
├── pages/              # страницы (Dashboard, Transactions, Categories, Budgets, Reports)
├── features/           # пользовательские действия
│   ├── add-transaction/    # форма новой операции
│   ├── add-category/       # форма новой категории
│   ├── add-budget/         # форма нового бюджета
│   └── delete-transaction/ # удаление операции с подтверждением
│       (в каждой: ui/ — компоненты, model/ — правила валидации)
├── entities/           # сущности предметной области
│   ├── category/  transaction/  budget/   # типы, API-клиенты, небольшие UI-компоненты
│   └── finance/        # общее хранилище данных (контекст) и вычисления: итоги месяца, расход по бюджету
└── shared/             # переиспользуемое: UI (PageHeader, DataState, Money, AppDialog), lib (формат, валидация), api, config
```

Данные приложения хранятся в `entities/finance` до подключение backend.

### Интерактивность и валидация
- Формы добавления операции, категории и бюджета (MUI), типизированные значения и свойства через TypeScript.
- Клиентская валидация (`features/*/model/validate.ts`): сумма и лимит — число больше нуля не более чем с 2 знаками после запятой; категория обязательна и должна соответствовать типу операции; название категории не пустое и не дублируется в рамках типа; описание не длиннее 255 символов. Ограничения согласованы с backend.
- Ошибка поля показывается после выхода из поля или при попытке сохранить форму; место под текст ошибки зарезервировано, чтобы форма не «прыгала».
- Экраны с данными обрабатывают состояния загрузки, ошибки (с кнопкой «Повторить») и отсутствия данных — компонент `shared/ui/DataState`.
- Фильтр по типу и поиск по описанию на экране транзакций; после добавления или удаления операции обновляются итоги на «Обзоре», суммы по категориям, бюджеты и отчёт.

### Анимация
Плавное появление страницы при переходе между разделами, появление карточек (итоги, категории, бюджеты), открытие форм и окон подтверждения, анимация шкалы бюджета, уведомления о результате действия.

### Проверка
Состояние ошибки проверяется остановкой backend: на экранах появляется сообщение «Нет соединения с сервером» с кнопкой «Повторить».

## 6. Backend

### Структура
```
backend/
├── app/
│   ├── api/          # маршруты: categories, transactions, budgets
│   ├── core/         # config (настройки), database (подключение и сессии)
│   ├── models/       # модели SQLAlchemy
│   ├── schemas/      # схемы валидации запросов и ответов
│   ├── services/     # операции с данными и бизнес-логика
│   └── main.py       # создание приложения
├── .env.example      # пример настроек без секретов
└── requirements.txt
```

### Модель данных
| Таблица | Поля | Назначение |
|---|---|---|
| `categories` | `id` (PK), `user_id` (FK → `users.id`), `name`, `type` (`income` / `expense`), `color`, `icon` | Категории доходов и расходов. Пара `name` + `type` уникальна в рамках пользователя |
| `transactions` | `id` (PK), `date`, `amount`, `description`, `category_id` (FK → `categories.id`) | Операции. `amount > 0`. Тип операции (доход или расход) определяется её категорией |
| `users` | `id` (PK), `email` (уникален), `password_hash`, `created_at` | Пользователи. Пароль хранится только в виде хеша Argon2id |
| `refresh_tokens` | `id` (PK), `user_id` (FK → `users.id`), `token_hash`, `expires_at`, `revoked` | Сессии входа: одна запись — один refresh token (хранится SHA-256 от токена) |
| `budgets` | `id` (PK), `category_id` (FK → `categories.id`), `month`, `monthly_limit` | Месячный лимит расходов по категории. Пара `category_id` + `month` уникальна, `monthly_limit > 0` |

Операции и бюджеты принадлежат пользователю через категорию. Все `id` — UUID. Связь «категория — операции» и «категория — бюджеты»: один ко многим.
- Категорию, к которой привязаны операции, удалить нельзя (`ON DELETE RESTRICT`, API отвечает `409`).
- При удалении категории её бюджеты удаляются вместе с ней (`ON DELETE CASCADE`).
- Бюджет можно задать только для категории расходов. Поле `month` всегда хранит первое число месяца.
- В ответе API у бюджета есть вычисляемое поле `spent` — сумма расходов по категории за месяц бюджета.
- Тип категории нельзя изменить, если у неё уже есть операции или бюджеты.

### API
Все маршруты имеют префикс `/api/v1`. Интерактивная документация: `http://localhost:8000/docs`.

| Ресурс | Методы |
|---|---|
| `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout` | `POST` (публичные) |
| `/auth/me` | `GET` |
| `/categories` | `GET` (фильтр `type`), `POST` |
| `/categories/{id}` | `GET`, `PATCH`, `DELETE` |
| `/transactions` | `GET` (фильтры `type`, `category_id`, `date_from`, `date_to`), `POST` |
| `/transactions/summary` | `GET` (параметр `months`, 1–24, по умолчанию 6) |
| `/transactions/{id}` | `GET`, `PATCH`, `DELETE` |
| `/budgets` | `GET` (фильтр `month`), `POST` |
| `/budgets/{id}` | `GET`, `PATCH` (только `monthly_limit`), `DELETE` |

Все ресурсы, кроме `/auth/*` (регистрация, вход, обновление, выход), требуют заголовок `Authorization: Bearer <access_token>`. Проверка работы сервера: `GET /health` (без префикса, публичная).

Денежные суммы (`amount`, `monthly_limit`, `spent`) API возвращает строками, например `"3200.00"`, чтобы не терять точность.

### Подготовка и запуск
Требуются Python 3.11+ и PostgreSQL.

**1. Создайте пользователя и базу данных** (в `psql` под администратором, например `psql -U postgres`):
```sql
CREATE USER finance WITH PASSWORD 'ваш_пароль';
CREATE DATABASE finance OWNER finance;
```

**2. Установите зависимости:**
```bash
cd backend
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

**3. Настройте окружение.** Скопируйте пример и впишите свои значения (файл `.env` в Git не попадает):
```bash
cp .env.example .env            # Windows: copy .env.example .env
```

**4. Запустите сервер:**
```bash
uvicorn app.main:app --reload
```
Таблицы создаются автоматически при первом запуске. API будет доступен по адресу `http://localhost:8000`.

## 7. Аутентификация и авторизация

### Схема работы
1. `POST /auth/register` — создаёт пользователя (email уникален, пароль 8–128 символов). Пароль хранится как хеш **Argon2id** (библиотека `pwdlib`, соль встроена в хеш).
2. `POST /auth/login` — по email и паролю выдаёт два токена:
   - **access token** — JWT (HS256), живёт 15 минут, передаётся в `Authorization: Bearer`;
   - **refresh token** — случайная строка, живёт 7 дней. В БД хранится только её SHA-256, поэтому утечка БД не даёт готовых токенов.
3. `POST /auth/refresh` — по действующему refresh token выдаёт новый access token. Ответ `401` при неизвестном, истёкшем или отозванном токене.
4. `GET /auth/me` — текущий пользователь по access token.
5. `POST /auth/logout` — отзывает refresh token текущей сессии (`revoked = true`). Другие сессии пользователя (другие браузеры) не затрагиваются. Повторный выход не считается ошибкой.

### Разграничение доступа
- Публичные: `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `/health`.
- Приватные: `/categories`, `/transactions`, `/budgets`, `/auth/me` — через зависимость `get_current_user` (`app/api/deps.py`).
- Данные принадлежат пользователю: категория хранит `user_id`, операции и бюджеты привязаны к нему через категорию. Список возвращает только записи пользователя; обращение к чужой записи по id даёт `404` (а не `403`, чтобы не раскрывать существование записи). Нельзя создать операцию или бюджет в чужой категории и перенести операцию в чужую категорию.

1. Поднять PostgreSQL и создать БД (см. раздел 6).
